The ±5% stepper: three answers, in order

You said "additive, not fixed", then "whatever it is in the real game". Getting to the real game took four sources and I was confidently wrong twice on the way.

What actually happens, recovered from the cache

Interface 105's +5% and −5% buttons both call client script 4112, passing the percentage as an argument. It edits varc 85 — a client variable — and sends nothing to the server. Varp 1111, which Darkan treats as the price, is the server-owned committed price, not what the buttons touch.

# client script 4112, rev 727, 62 ops
price = varc 85
if percent > 100 and price > 2045222520: new = 2147483647
elif percent < 100 and price <= 1:          new = 1
else:
    new = (int)((long) price * percent / 100)   # truncates toward zero
    if new == price: new += +1 if percent >= 100 else -1

So it compounds, it truncates, and there's a forced one-coin step when truncation would move nothing. Byte-identical at 371 bytes with every constant at the same offset across all six pre-EOC builds we hold, so it isn't a rev-727 artifact.

Where I was wrong, twice

First I called Darkan's (int)(price * 1.05) sourced. It's one fan-made server reverse-engineering behaviour it could only observe from outside — it fails the corroboration gate, and you were right to push.

Then I concluded it was unknowable and fell back to your preference. Also wrong: 2011Scape doesn't implement the offer screen at all, and three wiki revisions are silent, but the answer was in the cache the whole time. It's a client behaviour, which is exactly why no server source and no wiki records it.

And I was about to delete the one-coin minimum step as an invention. It's authentic. I had it backwards — only the round-to-nearest was wrong, and round vs truncate diverged on roughly half of all reachable prices (33→35 instead of 34).

The immutability gate can't see equal-value writes

It detects leaks by comparing the save for inequality, so a write storing a value already equal to what was there is invisible — real write-through that happens to be harmless on that data. I stopped claiming otherwise and added a probe that lends the riskiest helpers containers which refuse mutation, so it raises regardless of value. The remaining 44 unconverted deepcopy sites stay deep on purpose.

Also worth knowing

  2. Shop keeps its deep copy deliberately. Its buy path mutates nested values in place; a shallow copy aliased them to your live save and test_shop_logic.py caught it within seconds. That comment now says "do not optimize this one".

  5. Darkan has a fidelity fault, not just a wrong number. Those five server-side handlers shouldn't exist — setting varp 1111 can't change what the offer box displays. Written up in that project's memory bank as a failure class its audit plan lacks: implemented in the wrong tier.
