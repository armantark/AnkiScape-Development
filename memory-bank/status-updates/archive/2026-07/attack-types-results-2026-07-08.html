What shipped

🗂️
The generator now records the exact WeaponType id
EquipmentItem.weapon_type is read straight from the items.yml equipment block (Bronze dagger → 5 = DAGGER, Rune 2h sword → 7). Non-weapon and typeless rows (Cape, Toy kite) carry -1 and fall back to the UNARMED table.
📜
The parity table is transcribed verbatim into combat_data.py
WEAPON_TYPE_ATTACK_STYLES maps each WeaponType id to its ordered slot rows (weapon_style, style_type, xp_mode), each cite-and-pinned to AttackStyleData.kt. WEAPON_TYPE_UNARMED_STYLES (three crush slots) covers -1 and fists.
🧮
The melee formula reads the specific type — max() retired for the player
_combat_attack_bonus_from_totals / _combat_defence_bonus_from_totals now return attack_<type> vs the enemy’s matching defence_<type> when a concrete type is resolved. max() survives only on the enemy-attacks-player rolls, which carry no melee sub-type — exactly the parity-safe boundary.
🎛️
The selector lists real per-weapon slots, each with its type
Each row reads e.g. Aggressive (Slash) and shows the skills it actually trains. Storage stays backward-compatible: combat_attack_style keeps the weapon-style string, and a new orthogonal combat_attack_style_type (default "auto") picks the physical type within that slot.

The two-field model & the 2h anomaly

RuneScape keys the attack style on the slot ordinal, and one slot breaks the tidy “weaponStyle implies xpMode” assumption: the two-handed sword’s third slot is weaponStyle = AGGRESSIVE (so its effective-level bonus is the +3 strength of an aggressive swing) but xpMode = SHARED (so its XP splits three ways like controlled). It is the only slot where the two diverge, so the resolver threads them separately: effective-level uses the base weapon-style, XP uses the slot’s resolved xp_mode.

  • Unit ✓ the 2h aggressive/crush SHARED anomaly resolves to ("crush", "controlled") while aggressive/auto stays ("slash", "aggressive").

Balance note (as flagged in the plan): D1 is a real, deliberate combat shift. Against an enemy whose per-type defences differ, choosing the type it’s weak to now hits more often than before, since the old max() always used the enemy’s strongest defence. This is correct RuneScape behavior and was signed off as the recommended option.
Storage compatibility: existing saves are untouched — combat_attack_style keeps its meaning, and the new combat_attack_style_type defaults to "auto", which resolves to each weapon’s natural first-slot type. No migration needed.
