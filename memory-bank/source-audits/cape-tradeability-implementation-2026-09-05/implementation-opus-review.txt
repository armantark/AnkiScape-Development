## Finding 1 — High: the test reads an untracked file

Location: `tests/test_cape_tradeability.py`, `CapeTradeabilityDataTest.test_registry_and_market_preserve_equipment_identity`, first statement.

```python
snapshot = json.loads((ROOT / "memory-bank/source-audits/"
    "cape-tradeability-implementation-2026-09-05/owner-snapshot.json").read_text())
```

Consequence: the file bindings list four files, and `owner-snapshot.json` is not one of them. The diff does not add it. On a clean checkout the test fails with `FileNotFoundError`. A test must also not read the memory bank, because that directory holds work notes, not fixtures.

Fix: put the two expected definition dictionaries in the test module as literals, keyed by cape name. Delete the JSON read. If you must keep the file, track it under `tests/data/`.

## Finding 2 — High: the test can pass and prove nothing

Location: same test, `for retained in snapshot["definitions"]:`.

Consequence: an empty or short snapshot list makes the test pass with zero subtests. A third entry in the list raises `KeyError` in `CAPES[name]`. Both outcomes are silent or confusing.

Fix: add one assertion before the loop.

```python
self.assertEqual(
    {retained["fields"]["storage_key"] for retained in snapshot["definitions"]},
    set(CAPES),
)
```

## Finding 3 — High: the sell subtest depends on the buy subtest

Location: `_exercise_lifecycle`, the loop `for side, unit_price in (("buy", ...), ("sell", ...)):`.

Consequence: the sell branch asserts `addon.player_data["inventory"][name] == 0` after escrow. The item exists only because the buy branch collected it in the previous subtest. A buy failure produces a second, unrelated sell failure with a `KeyError`. The sell path never runs alone.

Fix: seed the item before the offer. `place_offer` saves player data, so no extra save is necessary.

```python
if side == "sell":
    addon.player_data["inventory"][name] = 1
```

## Finding 4 — Medium, verify first: the real collection runs under fakes

Location: `CapeTradeabilityRuntimeTest.setUp` and `test_buy_sell_persist_in_real_anki_collection`.

`setUp` calls `runtime_fixture._install_runtime_fakes()` for every test in the class. The second test then builds a real Anki `Collection`.

Consequence: if `_install_runtime_fakes()` replaces the `anki` package in `sys.modules`, the real `Collection` resolves its lazy imports to fake modules. The result is a false pass or a failure with no relation to the capes. If the helper fakes only `aqt`, this finding does not apply.

Fix: check the helper. If it touches `anki`, install the fakes in the two test methods instead of `setUp`, and install only the `aqt` fakes for the real-collection test.

## Finding 5 — Medium, verify first: a runtime import at module scope

Location: `tests/test_cape_tradeability.py`, import block.

```python
from ankiscape.runtime.runtime_actions_magic import _magic_alch_values
```

Consequence: this import runs before `setUp` installs the fakes. If `runtime_actions_magic` imports `aqt` at module scope, the whole test module fails at import time. Both test classes then fail, not only the data test. The environment guard on `storage_fixture.Collection` shows that Anki can be absent.

Fix: move the import into `test_existing_shop_and_alchemy_consumers_use_unchanged_values`, or read the alchemy values from `GE_ITEM_CATALOG` directly.

## Finding 6 — Low: the shop choice depends on dictionary order

Location: `test_existing_shop_and_alchemy_consumers_use_unchanged_values`.

```python
shop = next(shop for shop in SHOP_DATA.values()
            if shop["visibility"] == "visible" and shop["general_store"])
```

Consequence: a new shop entry changes which shop the test exercises. The hardcoded 0.3 sell rate then applies to a shop that never agreed to it.

## Finding 10 — Low: the expectations restate the production formula

Location: `test_existing_shop_and_alchemy_consumers_use_unchanged_values`, the `int(value * 0.3)`, `int(value * 0.4)`, and `int(value * 0.6)` expressions.

Two smaller points do not need a separate finding. `_JsonCollection` reaches into `self._store`, a private attribute of `_DummyCol`, and it breaks if that attribute is renamed. The product diff and the two count updates are correct and minimal. The new test module carries the risk. Findings 1 and 2 mean the data test can fail on a clean checkout or pass with no coverage.
